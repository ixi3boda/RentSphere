# Performance testing

This folder holds everything behind the performance numbers I quote for RentSphere on my
CV. Nothing here is a simulation or a mock: the dataset is generated into a real MySQL 8
container, the load is generated by Apache JMeter against the packaged Spring Boot image,
and `proof/` holds the screenshots and session log those runs produced.

If a number below is on my CV, this folder shows the command that produced it and, where the
number is a latency or throughput figure, the JMeter window that displayed it.

## Files

| File | What it is | Run with |
|---|---|---|
| `../Database/seed-large-dataset.sql` | Reseeds the schema with 5,000 users, 100,000 properties, 300,000 images, plus favorites, requests, contracts, installments and notifications. Truncates first, so it is idempotent. | `docker compose exec -T mysql mysql -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" RentSphereSchema < Database/seed-large-dataset.sql` |
| `db-benchmark.sql` | Index inventory plus `EXPLAIN` on the exact query shapes used by `PropertyRepository`. Answers "which index does the optimizer actually pick, and how many rows does it scan". | `docker compose exec -T mysql mysql -N RentSphereSchema -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" < Performance/db-benchmark.sql` |
| `rentsphere-load-test.jmx` | JMeter 5.6.3 test plan. One thread group, four samplers, randomized parameters, 1-2 s think time. Every knob is a `-J` property. | see steps 6 and 8 |
| `cities.csv`, `searchprefix.csv` | Data sources for the filter and search samplers (60 city/district/price combinations, 10 name prefixes) so consecutive iterations issue different queries. | loaded by the plan via `__CSVRead` |
| `docker-compose.perf.yml` | Compose override that maps the backend to host port 8090, because 8080 is taken on my machine. | `-f docker-compose.yml -f Performance/docker-compose.perf.yml` |
| `proof/` | Six window captures from the JMeter GUI itself, one JMeter HTML dashboard, Swagger UI and app screenshots, plus the raw session log. | browse |

## Environment the numbers were taken on

```
macOS 26.5, Darwin arm64
OpenJDK 17.0.18 (Homebrew) for the `-n` runs
OpenJDK 26 for the GUI runs (the JDK the JMeter launcher picked up)
Apache JMeter 5.6.3
MySQL 8.0 + Spring Boot backend + React frontend, all in Docker Compose
Backend image sha256:4ffd3b22560a... (see proof/run-2026-09-30.log)
```

Backend, MySQL and JMeter share one laptop, and other containers were running during the
2026-09-30 re-run. That inflates absolute latency and is the main reason re-runs differ by
10 to 30 percent. It does not affect the before/after comparison, which was measured on the
same machine minutes apart.

## Reproduce

```bash
# 0. secrets
cp .env.example .env          # fill real values; compose fails fast on ${VAR:?} if you skip
set -a; source .env; set +a

# 1. stack
docker compose -f docker-compose.yml -f Performance/docker-compose.perf.yml up -d mysql backend
curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" "localhost:8090/api/properties/filter?city=Cairo"

# 2. turn the query log off or the benchmark measures logging
docker compose exec mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "SET GLOBAL general_log=OFF;"

# 3. seed 100k listings (a few minutes)
docker compose exec -T mysql mysql -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" \
  RentSphereSchema < Database/seed-large-dataset.sql

# 4. index plans
docker compose exec -T mysql mysql -N RentSphereSchema -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" \
  < Performance/db-benchmark.sql > /tmp/db-bench.txt

# 5. a JWT for the authenticated sampler (seeded users have a placeholder hash, so register your own)
PERF_PASS='any-local-only-password'      # never a real credential; this account exists only in the container
curl -s -X POST localhost:8090/api/user/register -H 'Content-Type: application/json' \
  -d "{\"email\":\"perf@loadtest.local\",\"username\":\"perftest\",\"full_name\":\"Perf Test\",
       \"password_hash\":\"$PERF_PASS\",\"mobile_number\":\"01000000001\"}"
TOKEN=$(curl -s -X POST localhost:8090/api/user/login -H 'Content-Type: application/json' \
  -d "{\"email\":\"perf@loadtest.local\",\"password_hash\":\"$PERF_PASS\"}" \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["token"])')

# 6. the ladder. cd first: __CSVRead resolves relative to the working directory
cd Performance
for T in 25 50 100 200; do
  jmeter -n -t rentsphere-load-test.jmx \
    -Jhost=localhost -Jport=8090 -Jthreads=$T -Jramp=10 -Jduration=60 \
    -Jtoken="$TOKEN" -JresultFile=run_$T.jtl
done

# 7. JMeter's own HTML dashboard from any .jtl — open reports/run_50/index.html for the
#    per-endpoint percentile tables it computes
jmeter -g run_50.jtl -o reports/run_50

# 8. the same plan driven from the GUI, which is what proof/02-07 show
#    cd matters here too: __CSVRead resolves relative to the working directory
jmeter -t rentsphere-load-test.jmx -Jhost=localhost -Jport=8090 -Jtoken="$TOKEN"
#    type the thread count / ramp / duration into the Thread Group panel, point the
#    Results Writer at a concrete .jtl path, select Summary Report or Aggregate Graph,
#    then Run > Start.
```

`-n` is the right way to collect headline numbers: the GUI takes CPU from the same laptop
that is running the JVM under test, and its pacing is not what `-n` does. The GUI runs in
`proof/` exist to show the listeners really were driven against this stack, and they land
within a few percent of the `-n` runs at the same thread count (see the Results table), so
neither set of numbers depends on the other being believed.

## The N+1 behind the 40x

`GET /api/properties/search` and `/filter` map every `Property` row to a `PropertyDetails`
DTO. The original code called the single-property builder per row, so a page of listings
issued one `property_images` query each. With 300,000 image rows that is the endpoint
sitting at 6.2 s mean while everything else stayed under 100 ms.

The fix is `buildPropertyDetailsBatch` in
`Backend/src/main/java/com/example/RentSphere/Repository/PropertyRepository.java:83`. It
collects the page's property ids, then loads images for 500 ids at a time in one
`WHERE property_id IN (...)` through `JdbcTemplate`, and groups the result set into a map
keyed by property id. Three call sites use it (`:174`, `:340`, `:366`). Query count per page
goes from one-per-listing to one-per-500-listings.

To reproduce the baseline, point those call sites back at the single-property builder,
rebuild the image, and re-run step 6.

Raw `.jtl` sample files and the generated `reports/` dashboards are deliberately not kept in
this folder — they are large, machine specific, and re-creatable in a minute with step 6 or
step 8. The screenshots and the log are what carry the evidence.

One disclosure about the window titles in 02 to 07 (`gui-run.jmx`, `gui-r100.jmx`,
`gui-r200.jmx`, `gui-r100agg.jmx`): those are copies of `rentsphere-load-test.jmx` with the
thread count, ramp and duration written as literals instead of `${THREADS}` / `${RAMP}` /
`${DURATION}`, and with the Results Writer pointed at a concrete `.jtl` path. In GUI mode
JMeter does not substitute `-J` properties into the Results Writer's filename field, so it
refuses to start with the plan as committed. Nothing else in the plan was changed: same four
samplers, same header manager, same timers, same CSV sources.


## Limits of these numbers

* One machine runs load generator, app and database. Throughput is capped by that, not by
  the architecture.
* No cache layer, on purpose. Caching would hide the per-request database cost the exercise
  was about.
* 60 s per run is short enough that connection-pool and JIT warm-up are visible in the first
  few samples; the ramp is 10 s to absorb part of that.
* At 200 users latency degrades to a 1.4 s mean while errors stay at zero. That is the
  saturation point of this single-host setup. The next steps would be a read replica and a
  cache in front of the listing queries, not more indexes.
