# Performance testing

This folder holds everything behind the performance numbers I quote for RentSphere on my
CV. Nothing here is a simulation or a mock: the dataset is generated into a real MySQL 8
container, the load is generated by Apache JMeter against the packaged Spring Boot image,
and `proof/` holds the screenshots and session logs those runs produced.

If a number below is on my CV, this folder shows the command that produced it and, where the
number is a latency or throughput figure, the JMeter window that displayed it.

The plan was re-run on 2026-10-01 after the read path changed (listing queries are now paged,
`GET /api/properties/search` is gone, `GET /api/properties/stats` was added). Those 2026-10-01
rows are the ones the CV quotes, and `proof/` holds only the files those runs produced. An
earlier investigation on 2026-09-29 and 2026-09-30 measured the same problem against the
un-paged endpoints; it is described below for continuity, but its captures and session log are
not in this folder, because the October `before_50` run reproduces that baseline on the current
code and is the one every claim points at.

## Files

| File | What it is | Run with |
|---|---|---|
| `../Database/seed-large-dataset.sql` | Reseeds the schema with 5,000 users, 100,000 properties, 300,000 images, plus favorites, requests, contracts, installments and notifications. Truncates first, so it is idempotent. | `docker compose exec -T mysql mysql -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" RentSphereSchema < Database/seed-large-dataset.sql` |
| `db-benchmark.sql` | Index inventory plus `EXPLAIN` on the exact query shapes used by `PropertyRepository`, including the paged browse query, its `COUNT(*)` twin, the unanchored `LIKE` search and the batched `IN (...)` photo fetch. Answers "which index does the optimizer actually pick, and how many rows does it scan". | `docker compose exec -T mysql mysql -N RentSphereSchema -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" < Performance/db-benchmark.sql` |
| `rentsphere-load-test.jmx` | JMeter 5.6.3 test plan. One thread group, five samplers matching the requests the React app actually issues, randomized parameters, 1-2 s think time. Every knob is a `-J` property. | see steps 6 and 8 |
| `cities.csv`, `searchprefix.csv` | Data sources for the filter and search samplers (60 city/district/price combinations, 10 name prefixes) so consecutive iterations issue different queries. | loaded by the plan via `__CSVRead` |
| `docker-compose.perf.yml` | Compose override that maps the backend to host port 8090, for when 8080 is taken on the host. The 2026-10-01 runs did not need it. | `-f docker-compose.yml -f Performance/docker-compose.perf.yml` |
| `proof/` | Window captures from the JMeter GUI itself (the 2026-10-01 set) plus the raw session log for that day. | browse |

The five samplers, and why each is there:

| Label | Request | Where the app makes it |
|---|---|---|
| `GET /api/properties/stats` | three `COUNT(*)`s behind one call | Home hero and both dashboards |
| `GET /api/properties/filter` | city + district + price band, `page` randomized 0-5, `size=9` | the listings grid, including its pagination clicks |
| `GET /api/properties/filter?search` | free-text `search` prefix, `size=9` | the search box (replaces the old `/api/properties/search`) |
| `GET /api/properties/{id}` | random id in 1-100,000 | a listing detail page |
| `GET /api/user/me (authed)` | JWT in the `Authorization` header | every authenticated page load |

## Environment the numbers were taken on

```
macOS 26.5, Darwin arm64, Apple M5, 10 cores
Apache JMeter 5.6.3, java.version=26 for both the GUI and the -n runs on 2026-10-01
MySQL 8.0 + Spring Boot backend + React frontend, all in Docker Compose
Backend image sha256:85b8582baab9... (see proof/run-2026-10-01.log)
Backend published on host port 8080 (docker-compose default; no override needed)
```

Backend, MySQL and JMeter share one laptop, and other containers were running during the
re-runs. That inflates absolute latency and is the main reason re-runs differ by 10 to 30
percent. It does not affect the before/after comparison, which was measured on the same
machine minutes apart.

## Reproduce

```bash
# 0. secrets
cp .env.example .env          # fill real values; compose fails fast on ${VAR:?} if you skip
set -a; source .env; set +a

# 1. stack  (add -f Performance/docker-compose.perf.yml and use port 8090 if 8080 is busy)
docker compose up -d mysql backend
curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" "localhost:8080/api/properties/filter?city=Cairo"

# 2. turn the query log off or the benchmark measures logging
docker compose exec mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "SET GLOBAL general_log=OFF;"

# 3. seed 100k listings (a few minutes)
docker compose exec -T mysql mysql -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" \
  RentSphereSchema < Database/seed-large-dataset.sql

# 4. index plans
docker compose exec -T mysql mysql -N RentSphereSchema -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" \
  < Performance/db-benchmark.sql > /tmp/db-bench.txt

# 5. a JWT for the authenticated sampler (seeded users have a placeholder hash, so register your own)
PERF_PASS='any-local-only-password'      # never a real credential; this account exists only in the container
curl -s -X POST localhost:8080/api/user/register -H 'Content-Type: application/json' \
  -d "{\"email\":\"perf@loadtest.local\",\"username\":\"perftest\",\"full_name\":\"Perf Test\",
       \"password_hash\":\"$PERF_PASS\",\"mobile_number\":\"01000000001\"}"
TOKEN=$(curl -s -X POST localhost:8080/api/user/login -H 'Content-Type: application/json' \
  -d "{\"email\":\"perf@loadtest.local\",\"password_hash\":\"$PERF_PASS\"}" \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["token"])')

# 6. the ladder. cd first: __CSVRead resolves relative to the working directory
cd Performance
for T in 25 50 100 200; do
  jmeter -n -t rentsphere-load-test.jmx \
    -Jhost=localhost -Jport=8080 -Jthreads=$T -Jramp=10 -Jduration=60 \
    -Jtoken="$TOKEN" -JresultFile=run_$T.jtl
done

# 7. JMeter's own HTML dashboard from any .jtl — open reports/run_50/index.html for the
#    per-endpoint percentile tables it computes
jmeter -g run_50.jtl -o reports/run_50

# 8. the same plan driven from the GUI, which is what proof/01-07 show
#    cd matters here too: __CSVRead resolves relative to the working directory
jmeter -t rentsphere-load-test.jmx -Jhost=localhost -Jport=8080 -Jtoken="$TOKEN"
#    type the thread count / ramp / duration into the Thread Group panel, point the
#    Results Writer at a concrete .jtl path, select Summary Report or Aggregate Graph,
#    then Run > Start.
```

`-n` is the right way to collect headline numbers: the GUI takes CPU from the same laptop
that is running the JVM under test, and its pacing is not what `-n` does. The GUI runs in
`proof/` exist to show the listeners really were driven against this stack, and they land
within a few percent of the `-n` runs at the same thread count (see the Results table), so
neither set of numbers depends on the other being believed.

### 2026-09-29 and 2026-09-30, four samplers, un-paged listing queries

Measured before the listing endpoints were paged, so `/api/properties/filter` returned every
match instead of 9 rows and `/api/properties/search` still existed. Two numbers from that week
are still worth stating: 50 users against the un-paged code averaged 1,702 ms over 834 samples,
and the same laptop topped out around 70 req/s at 200 users while still reporting zero errors.

Those runs have no files in `proof/` — the captures and session log from that week are not kept

anyway: it is the current code with only the two regressed lines put back, so it is comparable
request-for-request with the `after_*` rows, which the September plan is not.

One caveat that applies to any of these tables: throughput has two defensible definitions.
JMeter's Summary Report divides by its own timing window, while the tables here divide by
first-to-last sample from the `.jtl`. For `after_200_gui` that gives 120.6 /s (`.jtl`), 121.3 /s
(window) and 121.0 /sec (the Summary Report capture). The CV says "about 120 req/s" because of
exactly this spread.

## What the 80x came from

`GET /api/properties/filter` maps every `Property` row on the page to a `PropertyDetails`
DTO, and each DTO carries its photo list. Two separate things were wrong, and this session
measured them apart.

**Un-bounded result set.** The endpoint used to return every row that matched the filters.
A search for `office` matches 14,286 of the 100,001 listings, so one browse request was
14,286 rows, 14,286 DTOs and an 8.2 MB JSON body (10.2 MB at its worst).

**N+1 on top of it.** Each of those rows was built with the single-property builder, which
issues two `property_images` queries. So the search sampler was issuing roughly 28,500
queries per request.

The fix is both halves: `filterProperties` now ends in `LIMIT ? OFFSET ?` with the page size
capped at 48 in `PropertyController`, and the rows are mapped through
`buildPropertyDetailsBatch` in
`Backend/src/main/java/com/example/RentSphere/Repository/PropertyRepository.java:86`. That
builder collects the page's property ids, loads images for 500 ids at a time in one
`WHERE property_id IN (...)` through `JdbcTemplate`, and groups the result set into a map
keyed by property id. Two call sites use it (`:175`, `:395`), so a 9-row page costs one
photo query instead of eighteen and a 48-row page costs one instead of ninety-six.

To see which half did the work, the runs below are all on 2026-10-01 with the same plan and
dataset, 50 users:

| Build | Listing page | Photo queries per request | Mixed avg | Search avg |
|---|---|---:|---:|---:|
| no paging, per-row builder (`before_50`) | up to 14,286 rows | ~28,500 | 1,808 ms | 8,036 ms |
| paging, per-row builder (`paged_nplus1_50`) | 9 rows | 18 | 23 ms | 84 ms |
| paging, per-row builder, 48-row cap (`paged_nplus1_48_50`) | 48 rows | 96 | 24 ms | 88 ms |
| paging, batched builder (`after_50`, shipped) | 9 rows | 1 | 22 ms | 82 ms |

Paging is the 80x. Once a page is capped, the N+1 has very little left to bite with, and the
batching is worth about 2 ms per request at the page sizes the UI uses. That is still the
right order of operations: the batching is what keeps the query count flat if a page size is
ever raised, and it is the only thing standing between `findByOwnerId` (which is not paged)
and a linear query count.

What is left is visible in `db-benchmark.sql`: the free-text search is an unanchored
`LIKE '%term%'` over `title`, `city` and `district`, which `EXPLAIN` reports as a full scan
of ~98,821 rows plus a filesort. That is the 82 ms, and it is the reason the search sampler
dominates the mixed average. No index fixes an unanchored `LIKE`; the next step is a
`FULLTEXT` index on `title` with `MATCH ... AGAINST`, or an external search index.

To reproduce the `before_50` build, delete the `LIMIT ? OFFSET ?` clause and its two params
from `filterProperties`, point its return at `buildPropertyDetails` per row instead of
`buildPropertyDetailsBatch`, rebuild the image, and re-run step 6.

Three disclosures about these screenshots. First, their window titles
(`guioct-g50.jmx`, `guioct-g100.jmx`, `guioct-g100agg.jmx`, `guioct-g200.jmx`,
`gui2-tg50.jmx`, `gui2-100agg.jmx`, `gui2-tg200.jmx`) are copies of
`rentsphere-load-test.jmx` with the thread count, ramp and duration written as literals
instead of `${THREADS}` / `${RAMP}` / `${DURATION}`, and with the Results Writer pointed at a
concrete `.jtl` path. In GUI mode JMeter does not substitute `-J` properties into the Results
Writer's filename field, so it refuses to start with the plan as committed. In the `*agg`
plans the Aggregate Graph is a clone of the Summary Report block with its `guiclass` changed
to `StatGraphVisualizer` — same sampler list, same save config. Nothing else in the plan was
changed. Second, in screenshots 02, 04, 05 and 07 the Label column has been dragged wider so
the endpoint names are legible; that is a display setting and changes no number. In 05 the
split between the table and the settings pane was also dragged down so the TOTAL row is
visible. Third, the Summary Report rounds its Average column to whole milliseconds and times
its throughput over the live window, so it can read 1 ms or 0.5 req/s away from the `.jtl`
aggregate of the same run; the Aggregate Graph's Graph Details table in screenshot 05 matches
its `.jtl` exactly, which is why the percentile claims point at that one.

## Limits of these numbers

* One machine runs load generator, app and database. Throughput is capped by that, not by
  the architecture.
* No cache layer, on purpose. Caching would hide the per-request database cost the exercise
  was about.
* 60 s per run is short enough that connection-pool and JIT warm-up are visible in the first
  few samples; the ramp is 10 s to absorb part of that.
* The paged browse query still sorts its whole match set (`Using filesort` in `EXPLAIN` 2a),
  so deep pages cost more than shallow ones. The plan asks for pages 0-5, which is what a
  browsing session does; page 1,000 would not be this fast.
* The free-text search is a full scan with an unanchored `LIKE`, and it is 82 ms of the mixed
  average. It is the next thing to fix, and the fix is a `FULLTEXT` index rather than another
  B-tree index.
* At 200 users the mixed mean is 22 ms with zero errors on this dataset, so the single-host
  saturation point that the September runs hit at ~70 req/s is no longer reached inside 60 s.
  That is a consequence of paging the listing queries, not of the machine being faster: the
  same laptop saturated at 70 req/s when a search request moved 8 MB.
